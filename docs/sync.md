# 매일 아침 브런치 글 목록 받기

큰 계획의 2단계 ‘핵심 기능’에 필요한 자동 동기화입니다. 장면을 자동으로 선정하는 기능은 아닙니다. 발행된 글 목록을 받아 콘텐츠 세션이 새 장면 초안을 만들 수 있게 합니다.

## 언제, 어떻게 돌아가나

- 한국 시간 매일 아침 6시(UTC 21시)에 GitHub Actions가 실행합니다. GitHub 사정에 따라 시작은 늦어질 수 있습니다.
- 저장소의 **Actions → 브런치 매일 동기화 → Run workflow**에서 손으로도 실행할 수 있습니다.
- `npm ci`로 준비한 뒤 기존 `pipeline/sync.ts`를 실행합니다. `.cache/brunch`는 GitHub의 캐시 기능으로 이어 써서 같은 글을 다시 받는 일을 줄입니다.
- 내용이 같으면 생성 시각과 나열 순서만 바뀐 파일은 원래대로 돌리고, PR 없이 끝납니다.
- 새 글·바뀐 글·목록에서 빠진 글이 있으면 **원문 대조 → 앱 데이터 만들기 → npm run check**를 순서대로 실행합니다. 하나라도 실패하면 실행은 실패로 끝나고 새 PR을 열지 않습니다. 이미 열려 있던 PR도 실패한 내용으로 갱신하지 않습니다.
- 모두 통과하면 `bot/brunch-sync` 가지에서 PR을 만듭니다. 같은 가지의 PR이 열려 있으면 새 결과로 갱신합니다. 합치는 것은 사용자입니다.

실제로 커밋하는 파일은 `content/brunch/index.json`과 내용이 달라진 `public/data/scenes.json`뿐입니다. 앱 데이터도 생성 시각만 달라졌다면 커밋하지 않습니다. 글 전문이 있는 `.cache/`, 장면 초안, 사진 파일, 키는 올리지 않습니다. 카카오 키나 브런치 로그인도 필요 없습니다.

PR 제목은 `브런치 새 글 N편 (YYYY-MM-DD)`이고 날짜는 한국 시간입니다. 새 글이 없고 기존 글만 바뀐 경우에도 제목의 N은 0입니다. 자세한 변경은 설명의 세 목록에서 봅니다. 글 제목과 공개 브런치 주소만 적으며 글 전문은 넣지 않습니다.

## 아침에 PR이 오면 할 일

1. PR 설명의 **새 글·바뀐 글·목록에서 빠진 글**을 확인하고 글 주소를 열어 봅니다.
2. 콘텐츠 세션에 새 글의 장면 초안을 부탁합니다. 자연 풍경 종류와 한 줄 소개는 기존처럼 초안 → 사용자 확인 순서입니다.
3. **검사는 동기화 워크플로에서 통과** 옆의 실행 기록을 확인한 뒤 PR을 합칩니다. 새 장면 초안은 콘텐츠 세션의 별도 확인과 PR로 진행합니다.

기본 `GITHUB_TOKEN`으로 만든 PR에는 다른 `ci` 검사가 자동 실행되지 않습니다. 그래서 동기화 워크플로 안에서 먼저 검사를 모두 마치고 그 실행 링크를 PR 설명에 남깁니다. ([GitHub의 실행 규칙](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow))

## 처음 켜기 전에 필요한 GitHub 설정

새 수동 실행 워크플로는 먼저 기본 가지 main에 들어가야 합니다. PR을 합치는 결정은 사용자입니다. ([GitHub 수동 실행 안내](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow))

2026-10-05에 읽어 본 저장소 설정은 **자동 PR 만들기 허용이 꺼져 있었습니다**. 자동 PR을 만들려면 사용자가 다음 설정을 허용해야 합니다.

**Settings → Actions → General → Workflow permissions → Allow GitHub Actions to create and approve pull requests → Save**

설정 이름에 ‘approve’도 들어 있지만 이 워크플로는 PR을 승인하거나 합치지 않습니다. 기본 권한을 전부 쓰기로 넓힐 필요도 없습니다. 이 작업에 필요한 쓰기 권한만 워크플로의 동기화 작업에 지정했습니다. 외부 서비스 설정은 사용자의 결정이라 이번 작업에서 바꾸지 않았습니다. ([GitHub 설정 안내](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository))

## 실패하면 무엇을 보나

Actions에서 빨간 실행을 열고 **동기화와 변경 검사** 단계의 마지막 오류를 봅니다.

| 오류가 난 명령 | 확인할 곳 |
|---|---|
| pipeline/sync.ts | 브런치 연결, 글 번호, 페이지 구조 변경 여부 |
| pipeline/scenes/check-cli.ts | 콘텐츠 세션에 원문 대목·사진·날짜·좌표 오류 확인 부탁 |
| pipeline/scenes/build.ts | 글 목록과 장면 초안의 연결 확인 |
| npm run check | 실패한 테스트·타입·비밀 키 검사·예산 이름 확인 |
| PR 올리기 | 위의 자동 PR 만들기 설정, 또는 다른 테스트 가지에 열린 봇 PR 확인 |

브런치 연결이 잠깐 실패한 경우에만 나중에 다시 실행합니다. 원문이나 초안 오류를 자동으로 고치지는 않습니다. GitHub 알림 설정에 따라 실패 메일이 옵니다.

## 개발자가 확인할 세 가지 실행

수동 실행은 선택한 가지의 파일을 대상으로 합니다. 예약 실행의 대상은 main입니다. main에 바로 커밋하는 단계는 없습니다. 테스트 가지에서 수동 실행하면 PR의 합칠 대상도 그 테스트 가지입니다. 테스트 PR은 확인 후 닫고 main에 합치지 않습니다. 동일한 `bot/brunch-sync`를 쓰므로 다른 대상을 향한 봇 PR이 열려 있으면 실행은 덮어쓰기 전에 멈춥니다.

1. **변경 없음:** 최신 글 목록이 있는 가지에서 수동 실행합니다. ‘글 목록 변경 없음.’으로 끝나고 봇 PR이 새로 생기지 않아야 합니다. 실제 새 글이 있다면 먼저 정상 동기화 PR을 확인·합친 뒤 다시 실행합니다.
2. **한 글 복원:** main에서 테스트 가지를 만들고 글 목록의 `stories`에서 한 글을 뺍니다. `count`도 남은 글 수에 맞춥니다. 이 가지에서 수동 실행하면 빠진 글이 다시 들어오고 이 테스트 가지를 대상으로 한 봇 PR이 생겨야 합니다. 실행 링크와 PR 링크를 기록하고 테스트 PR은 닫습니다.
3. **검사 실패:** 별도 테스트 가지에서 위처럼 한 글을 빼고, `tests/unit/daily.test.ts`에 의도적으로 실패하는 테스트를 추가합니다. 수동 실행이 `npm run check`에서 실패하고 새 봇 PR이나 실패한 내용의 갱신이 없어야 합니다. 실행 링크를 기록합니다. main 파일은 바꾸지 않습니다.

## 이번 개발의 확인 기록

구현 전에 `npm run test -- tests/unit/daily.test.ts`에서 **16개 모두 실패**를 확인하고 검사 전용 커밋으로 기록했습니다. 구현 뒤 16개가 통과했습니다. 작은 임시 폴더에서 목록 한 글 복원·생성 시각만 변경·네 명령 각각의 실패·앱 데이터의 생성 시각 복원을 확인합니다. 임시 폴더만 지우며 실제 목록은 바꾸지 않습니다.

위 테스트는 PR 준비까지의 동작과 워크플로의 커밋 범위를 확인하는 검사입니다. 실제 GitHub 수동 실행의 증빙은 별개입니다. 처음 만든 워크플로의 main 합치기와 자동 PR 권한 허용 전에는 세 실행 링크를 확보할 수 없으므로 PR 설명에 미확인 상태로 적습니다. 기본 동기화 스크립트는 Linux 실행 방식이므로 실제 동기화는 GitHub의 Ubuntu 실행 환경에서 확인합니다.
